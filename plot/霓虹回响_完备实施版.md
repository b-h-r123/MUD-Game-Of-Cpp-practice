# 《霓虹回响（Neon Echo）》完整可执行版策划案

> **版本：1.0 完备实施版**
> 
> **项目类型：** 赛博朋克题材 C++ Windows 控制台 MUD / 回合制 RPG
> 
> **目标：** 本文不是概念性策划，而是可以直接交给 C++ 开发模型或团队进行实现的“开发规格”。除非本文件明确允许，否则不要自行增加系统。

---

# 一、项目定位

## 1.1 项目名称

**《霓虹回响（Neon Echo）》**

宣传语：

> **在霓虹与废墟之间，活到最后。**

## 1.2 游戏类型

赛博朋克、文字 MUD、回合制 RPG、六房间固定关卡、单线闯关。

运行平台：

- Windows
- C++ 控制台程序
- 不使用图形界面
- 通过文字、ASCII 边框、角色图案、血条、日志表现游戏

## 1.3 项目目标

本项目以“一周左右完成”为目标，强调：

1. 功能完整
2. 代码容易理解
3. 类职责清晰
4. 能够体现 C++ 面向对象、STL、文件操作、随机数等课程知识
5. 能够完整演示“开始游戏 → 战斗 → 成长 → Boss → 通关”
6. 所有核心规则明确，不依赖开发人员临时决定

# 二、核心玩法

玩家扮演佣兵 R-17，从天穹城外围一路深入企业核心区域。

固定流程：

```text
主菜单
  ↓
新游戏 / 读取存档
  ↓
房间 1
  ↓
战斗 / 事件 / 奖励
  ↓
关卡准备界面
  ├─ 升级
  ├─ 黑市
  ├─ 查看角色
  ├─ 保存
  └─ 进入下一房间
  ↓
房间 2
  ↓
……
  ↓
房间 5
  ↓
最终准备
  ↓
房间 6：NEON-X Boss
  ↓
胜利 / Game Over
```

核心循环：

> **战斗 → 获得 EXP / GOLD / 道具 → 升级或购买 → 下一房间 → Boss**

# 三、明确的游戏状态

为了避免开发时出现“某个界面能不能进入”的争议，游戏只允许存在以下状态：

```text
MAIN_MENU
PREPARATION
BATTLE
EVENT
UPGRADE
SHOP
STATUS
SAVE
LOAD
VICTORY
GAME_OVER
EXIT
```

推荐由 `Game` 使用一个枚举控制：

```cpp
enum class GameState
{
    MAIN_MENU,
    PREPARATION,
    BATTLE,
    EVENT,
    UPGRADE,
    SHOP,
    STATUS,
    VICTORY,
    GAME_OVER,
    EXIT
};
```

# 四、固定六房间结构

游戏永远只有六个房间，不生成随机地图，不允许跳关，不允许重复进入已经完成的房间。

| 房间  | 名称      | 类型        | 核心内容         |
| --- | ------- | --------- | ------------ |
| 1   | 废土入口    | 教学战斗      | 熟悉普攻、技能、道具   |
| 2   | 黑市街区    | 普通战斗 + 事件 | 第一个随机事件      |
| 3   | 工业工厂    | 精英战斗      | 提高敌人强度       |
| 4   | 实验区域    | 特殊战斗      | 异常状态         |
| 5   | 企业核心区   | 高级战斗      | Boss 前最终资源检查 |
| 6   | NEON 核心 | Boss      | NEON-X 最终战   |

房间解锁规则：

```text
初始：只解锁房间1

完成房间1 → 解锁房间2
完成房间2 → 解锁房间3
完成房间3 → 解锁房间4
完成房间4 → 解锁房间5
完成房间5 → 解锁房间6
```

不得出现跳过房间的功能。

# 七、升级系统

## 7.1 升级触发

玩家通过击败敌人获得 EXP。

当：

```text
EXP >= 当前等级 × 100
```

立即升级。

例如：

```text
Lv1 → Lv2：100 EXP
Lv2 → Lv3：200 EXP
Lv3 → Lv4：300 EXP
...
Lv9 → Lv10：900 EXP
```

## 7.2 最大等级

```text
MAX_LEVEL = 10
```

达到 10 级后不能继续升级。

## 7.3 经验处理

升级时保留超出的经验。

例如：

```text
Lv1
EXP = 95

击败敌人获得 20 EXP

变为：

Lv2
EXP = 15
```

如果一次获得大量经验导致连续升级，则允许连续升级：

```text
while exp >= requiredExp && level < MAX_LEVEL
```

## 7.4 升级奖励

每升 1 级：

```text
level + 1
attributePoint + 1
```

玩家必须手动选择属性点用途。

## 7.5 属性点选择

每 1 点只能选择一个：

```text
1. MAX_HP +20
2. ATK +5
```

属性点可以保存，不要求立刻使用。

例如：

```text
属性点：2

1. MAX_HP +20
2. ATK +5
3. 暂不使用
```

禁止：

- 一次点击同时加两种属性
- 重新分配已使用的属性点
- 使用金币替代属性点升级

## 7.6 MAX_HP 增加后的当前 HP

每次：

```text
MAX_HP +20
```

同时：

```text
HP +20
```

例如：

```text
100 / 100
升级生命

变为：

120 / 120
```

这样升级生命不会产生“最大生命提高但当前生命不变”的不直观情况。

# 八、战斗系统

## 8.1 基本规则

战斗采用严格回合制。

```text
玩家回合
 ↓
玩家选择行动
 ↓
执行行动
 ↓
检查敌人死亡
 ↓
敌人回合
 ↓
处理敌人行动
 ↓
检查玩家死亡
 ↓
进入下一回合
```

## 8.2 玩家四种行动

每个玩家回合固定显示：

```text
1. 普通攻击
2. 电磁脉冲
3. 义体过载
4. 使用道具
```

没有额外“防御”选项。

## 8.3 普通攻击

```text
消耗 Energy：0
伤害：Player.ATK
```

公式：

```text
damage = player.attack;
```

## 8.4 技能 1：电磁脉冲

```text
名称：电磁脉冲
Energy：2
伤害：ATK + 15
```

公式：

```text
damage = player.attack + 15;
```

特点：

- 低能耗
- 稳定输出
- 无副作用

## 8.5 技能 2：义体过载

```text
名称：义体过载
Energy：3
伤害：ATK × 2
副作用：玩家 HP -5
```

公式：

```text
damage = player.attack * 2;
player.hp -= 5;
```

限制：

如果玩家当前 HP <= 5，仍然允许使用，但最终 HP 必须被限制为：

```text
HP = 1
```

不能因为技能自损直接死亡。

## 8.6 能量系统

最大能量：

```text
MAX_ENERGY = 5
```

每场战斗开始：

```text
energy = maxEnergy;
```

能量不会每回合自动恢复。

只有：

1. 使用能量电池
2. 下一场战斗开始

可以恢复。

## 8.7 能量不足

使用技能前检查：

```cpp
if (energy < skill.energyCost)
```

显示：

```text
能量不足！
当前 Energy：1
需要 Energy：3
```

本回合不消耗行动。

玩家重新选择。

## 8.8 道具行动

使用一个道具也算玩家本回合行动。

使用道具后：

```text
玩家回合结束
→ 敌人行动
```

# 九、道具系统

## 9.1 四种道具

| 道具   | 价格    | 效果                   |
| ---- | -----:| -------------------- |
| 医疗包  | 50 G  | 恢复 40 HP             |
| 能量电池 | 80 G  | 恢复 2 Energy          |
| 强化芯片 | 150 G | ATK +5               |
| 生命芯片 | 150 G | MAX_HP +10，同时 HP +10 |

统一规则：

```text
HP 不超过 MAX_HP
ENERGY 不超过 MAX_ENERGY
```

## 9.2 道具是否消耗

确定：

- 医疗包：消耗 1
- 能量电池：消耗 1
- 强化芯片：消耗 1
- 生命芯片：消耗 1

## 9.3 强化芯片

使用后：

```text
ATK += 5
```

属于永久成长，不是本场战斗临时效果。

## 9.4 生命芯片

使用后：

```text
maxHp += 10;
hp += 10;
```

但不能超过新的最大生命值。

## 9.5 道具使用界面

```text
====================================
             INVENTORY
====================================

HP：80 / 120
Energy：2 / 5

1. 医疗包      ×2
2. 能量电池    ×1
3. 强化芯片    ×1
4. 生命芯片    ×0
5. 返回

请选择：
>
```

数量为 0 的道具不可使用。

# 十二、能量和生命的房间间规则

这是原方案中必须明确的部分。

## 12.1 进入下一场战斗

进入任何新战斗：

```text
energy = maxEnergy;
```

## 12.2 战斗后的 HP

**不会自动恢复。**

即：

```text
上一场结束 50 / 120
下一场开始仍然是 50 / 120
```

恢复只能通过：

- 医疗包
- 生命芯片
- 游戏中的其他明确奖励

## 12.3 为什么这样设计

这样可以让：

- 战斗决策有意义
- 医疗包有意义
- 商店有意义
- 玩家需要考虑资源

而又不会增加复杂机制。

# 十三、异常状态

## 13.1 中毒

只在特定敌人技能中触发。

效果：

```text
每回合开始时 -5 HP
持续 3 回合
```

字段：

```cpp
bool poisoned;
int poisonTurn;
```

## 13.2 电击

效果：

```text
下一回合造成伤害时 -5
持续 1 回合
```

字段：

```cpp
bool shocked;
int shockTurn;
```

## 13.3 状态处理时机

玩家受到状态：

```text
敌人攻击 / 技能
 ↓
附加状态
 ↓
下一回合开始处理状态
```

中毒：

```text
回合开始
→ HP -5
→ poisonTurn--
```

归零后解除。

电击：

```text
下一次造成伤害
→ damage -5
→ shocked = false
```

## 13.4 保护规则

伤害最低为 0：

```cpp
damage = max(0, damage);
```

状态伤害不能把 HP 显示为负数。

# 十六、敌人 AI

## 16.1 普通敌人

普通敌人每回合从动作池随机选择：

```text
0：普通攻击
1：技能攻击
2：防御
```

但为了避免某些基础敌人出现不需要实现的复杂行为，具体敌人行动必须使用以下表。

| 敌人    | 0   | 1    | 2   |
| ----- | --- | ---- | --- |
| 废土鼠   | 普攻  | 普攻   | 普攻  |
| 街头猎犬  | 普攻  | 普攻   | 防御  |
| 改造人   | 普攻  | 普攻   | 防御  |
| 黑客佣兵  | 普攻  | 技能   | 防御  |
| 攻击无人机 | 普攻  | 电击   | 防御  |
| 重装保镖  | 普攻  | 强力攻击 | 防御  |
| 企业猎杀者 | 普攻  | 强力攻击 | 防御  |

## 16.2 防御

防御不是玩家行动选项。

敌人防御后：

```text
下一次受到伤害 × 0.5
```

整数取整：

```cpp
damage = damage / 2;
```

防御效果只持续到该敌人的下一次行动。

如果防御后的下一次伤害已经被触发，则立即解除。

## 16.3 特殊敌人技能

### 攻击无人机：电击

```text
伤害 = ATK
附加 shocked
```

### 重装保镖：强力攻击

```text
伤害 = ATK + 5
```

### 企业猎杀者：强力攻击

```text
伤害 = ATK + 8
```

### 黑客佣兵：干扰

```text
伤害 = ATK - 3
附加 shocked
```

如果伤害小于 0：

```text
damage = 0
```

### 实验体 X-01

```text
普通攻击
```

# 三十五、单场战斗伪代码

```text
battle()

    energy = maxEnergy

            damage = ATK + 15

        检查升级
        保存游戏
```

# 四十七、代码实现原则

1. 不使用复杂设计模式。
2. 不使用第三方游戏引擎。
3. 不把所有代码全部写进 `main.cpp`。
4. 类之间通过清晰的函数交互。
5. 不为了使用 STL 而强行增加不必要的数据结构。
6. 每完成一个模块立即测试。
7. 所有菜单都必须处理非法输入。
8. 所有 HP / Energy / Gold 修改都必须做边界检查。
9. 所有存档数据读取后必须校验。
10. 游戏任何阶段都不能因为普通用户输入而崩溃。

# 五十一、原方案中已修正的问题

本版本已经明确修正以下容易导致开发失败的问题：

### 1. 房间敌人数量不明确

现已规定每个房间的战斗顺序和敌人。

### 2. 战斗是否多敌人同时出现不明确

现改为：

> **一个敌人一个敌人依次战斗。**

### 3. HP 是否自动恢复不明确

现规定：

> **不自动恢复。**

### 4. 能量何时恢复不明确

现规定：

> **每场新战斗开始恢复满。**

### 5. 技能自损可能导致玩家死亡

现规定：

> 义体过载最低将玩家保留在 1 HP。

### 6. 强化芯片价格前后不一致

现统一为：

> **150 G。**

### 7. 生命芯片效果不明确

现统一为：

> **MAX_HP +10，同时 HP +10。**

### 8. XP 溢出不明确

现规定：

> 保留溢出经验，允许连续升级。

### 9. 保存的是当前房间还是下一房间不明确

现规定：

> `CURRENT_ROOM` 表示下一个准备进入的房间。

### 10. 自动保存时机不明确

现规定：

> 房间完整结束并结算奖励后自动保存。

### 11. 存档损坏时行为不明确

现规定：

> 检查版本和数据合法性，失败则返回主菜单，不能崩溃。

### 12. 敌人防御的实际效果不明确

现规定：

> 下一次受到伤害减半。

### 13. 异常状态什么时候处理不明确

现规定：

> 回合开始处理中毒；下一次造成伤害时处理电击减伤。

### 14. Boss 技能和阶段不完整

现规定：

> 150 HP 以下进入狂暴，并解锁核心过载。

### 15. 六个核心类与 Battle 模块冲突

现规定：

> Battle 默认作为 Game 的成员函数实现，不强制增加核心类。

### 16. 输入错误没有完整规则

现规定：

> 所有数字输入都必须防止非法输入和越界。

### 17. 原策划章节编号存在缺失/重复

正式开发文档应重新从 1 开始编号，不再沿用原稿中缺失的“十四、五十”等编号。

# 五十三、最终定位

> **《霓虹回响（Neon Echo）》是一款以赛博朋克世界观为背景的 C++ Windows 控制台回合制 MUD 闯关游戏。玩家通过六个固定房间，与逐渐增强的敌人进行战斗，使用普通攻击、两种技能和道具管理 HP 与 Energy，通过 EXP、金币和属性点成长，在房间之间进行升级、商店购买与存档，最终挑战进入狂暴状态的 NEON-X。项目采用 Game、Player、Enemy、Room、Skill、Item 六个核心对象组织逻辑，并结合 STL、随机数和 fstream 实现战斗、事件、背包及存档功能。**

> 本版本的目标不是做“大而全”，而是保证：**规则明确、代码可落地、流程完整、数值可运行、能够在一周左右完成并用于课程展示。**
